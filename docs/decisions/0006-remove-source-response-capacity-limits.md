# ADR-0006: 全データソースの取得・解析に容量上限を設けない

| 項目 | 値 |
| --- | --- |
| 状態 | Accepted |
| 決定日 | 2026-09-26 |
| 決定者 | リポジトリ所有者 |
| 要件との整合確認日 | 2026-09-26 |
| 対応仕様 | データソースと証拠の方針 1.2、6.1節 |
| 適用範囲 | 詳細解析MVPの全sourceと共通transportにおける取得・展開・解析の容量制限 |
| 実装状態 | 容量上限の撤廃を実装済み。live有効化は別判断 |

## コンテキスト

従来は、想定外の巨大応答や圧縮データの展開によるメモリ・保存領域の消費を抑えるため、
HTTP応答bytes、ZIP/XLSX内部の展開量、圧縮率、member数、XBRLのfact件数・値長に上限を設けていた。
`DEC-20`ではsource・operation別の応答上限を承認し、`yfinance`のchartには32 MiBを適用していた。
さらにcookie・crumb・consentへ小さな上限を設ける案を提示した。

これに対して所有者は、容量で取得を制限する必要はなく、OOMが発生する可能性を受容すると決定した。
その判断理由は`yfinance`固有ではないため、他sourceにも同じ方針を適用するよう指示した。

## 決定

全sourceについて、資源消費量だけを理由とするアプリケーション独自の容量上限を設けない。
対象は`yfinance`、EDINET、日本銀行、JPX、および共通transportである。source固有の例外にはしない。

撤廃する制限:

- HTTP応答の受信時・展開後・保存前のbytes上限。
- アーカイブのmember単体・合計の展開bytes、圧縮率、member数の上限。
- XLSX内部ファイルのbytes上限。
- XBRLのfact件数と、容量保護だけを目的としたfact値・typed valueの最大長。

OOMの回避を保証せず、OS・コンテナ等のメモリ設定は変更しない。OOM時の自動再試行は追加しない。
互換用の`max_response_bytes`フィールドは`None`のみを受け付け、有限値の容量制限を有効化しない。

### 維持する検証と制御

容量上限の撤廃は、入力を無検証で採用することを意味しない。次は撤廃対象ではない。

- media type、encoding、JSON・XML・ZIP等の形式検証。
- path traversal、重複path、symlink、暗号化、許可しない圧縮形式等の検証。
- hash、記録されたmember長と実bytesの一致、inventory整合。
- 識別子、QName、参照、日付、dimension、nil/value等の意味的な制約。
- rate、concurrency、queue、cooldown、timeout、retry・redirect・fallbackの制御。
- 認証、秘密値の非露出、raw公開の整合性、source別live acceptance。

記録長との一致は「宣言されたbytesと実体が同じか」の検証であり、固定容量上限ではない。
本決定によって未確定の補助応答形式を承認したり、live停止を解除したりしない。

## 採用理由

1. 本MVPでは、容量を理由にデータを拒否してOOMを予防することを、所有者が必要な要件としていない。
   OOMの可能性を受容するという明示的な運用判断を優先する。
2. データが大きいことだけでは内容が不正とは限らない。固定値を超えた正規の応答を拒否するより、
   内容・形式・整合性を検証して処理する方針を採る。
3. 提案した小さな補助応答上限は実測やprovider保証に基づく値ではなく、調整・承認・保守の対象を
   増やしていた。所有者が不要と判断した容量保護のために、その複雑さを維持しない。
4. 同じ資源消費上の懸念に対する判断なので、`yfinance`だけを特例にして他sourceへ上限を残さない。

これは容量制限が一般に無意味または無害であるという主張ではなく、本MVPの要件とリスク受容に
基づく選択である。

## 検討した代替案

- source・operation別の小さな上限を維持する: 所有者が不要とした容量保護と数値管理を残すため不採用。
- 全応答を共通32 MiBへ統一する: 設定は簡素になるが、容量だけによる拒否を残すため不採用。
- `yfinance`だけ上限を撤廃する: 判断理由が全sourceに共通するため不採用。

## 結果と受容するリスク

正規のデータが独自の容量閾値だけで拒否されなくなり、上限値の設定・調整が不要になる。
一方、大きな応答・圧縮データによってメモリ、CPU時間、保存領域の消費が増える可能性がある。
OOMやprocess終了、取得・解析失敗が起こり得ることを許容し、完了や無制限の処理能力は保証しない。
容量以外の安全性・整合性の検証は引き続き必要である。

## 既存決定との関係

`DEC-20`と従来の実装計画のうち、応答・展開量等の容量上限に関する部分を置き換える。
media type・encoding等の条件、ADR-0001の通信調整、ADR-0005の公開・復旧境界は変更しない。
容量上限を再導入する場合は、本ADRを黙って変更せず、必要になった要件と理由を後続の決定へ記録する。

## 検証条件

1. 旧HTTP応答上限を超えるデータを途中で切り捨てず受け渡せる。
2. 旧アーカイブサイズ・圧縮率・member数、fact値長等の上限を超える正常fixtureを受理する。
3. 形式違反、危険なpath、hash・記録長・inventory不一致の拒否が維持される。
4. rate制御とlive停止が容量制限の撤廃に伴って変更されていない。
5. 容量無制限の確認のために実際のOOMをテストで発生させる必要はない。
