## 1. 目的

詳細解析MVPのモデル配置、独立性、一次レビュー、限定再調査、争点分類、
Antigravity追加監査、監査結果の適用、人間へのエスカレーションを定める。

## 2. モデル配置

| 役割 | ドラフト要件 |
| --- | --- |
| オーケストレーター | Codex系またはClaude系から設定で1つ選び、実際のモデルと設定を記録する |
| 通常作業者 | Codex系1つ、Claude系1つを使用する |
| 一次レビューワー | 各実行に1つ割り当て、オーケストレーターと異なるモデル系統にする |
| 条件付き第三者監査 | Antigravityを重要な未解決争点にだけ使用する |

特定のモデル名を要件へ固定しない。利用可能性、構造化出力、コンテキスト長、
費用、安全設定を確認して設定ファイルで選び、実際に利用したモデル、版、論理設定、
製品固有設定を`manifest`へ記録する。

## 3. 独立性

- Codex系とClaude系の作業者へ、同じ対象銘柄、調査条件、初期共通証拠、評価Policy、
  Web探索Policyを渡す。
- 独立分析が完了するまで、他作業者、オーケストレーター、レビューワーの暫定結論を渡さない。
- 各作業者は証拠外の事実を補わず、事実、推論、仮説、欠損、反証条件を区別する。
- Codex系とClaude系の作業者は、互いの検索結果を見ずにAgent内蔵Web検索で独立探索する。
  検索結果を確定事実の根拠にせず、候補URL、検索記録、支持・反証し得る主張を返す。
  候補資料に基づく初回分析は未検証の仮説として区別し、有効な`evidence_id`を付けない。
- オーケストレーターは候補資料を承認済み取得・検証工程へ渡す。検証済み資料の和集合を
  共通証拠として両作業者へ差し戻し、相手の暫定結論を渡さずに影響範囲を再分析させる。
- 統合・一次レビュー・最終判定で確定事実の根拠にできるのは、検証済み共通証拠だけとする。
- 統合時に不一致を多数決、平均、モデル権威によって消さない。
- 一次レビューワーへは統合結果と根拠を渡すが、望ましい合否を指示しない。
- Antigravityへは作成主体を匿名化した争点パケットだけを渡す。

分析の独立性は検索語、探索結果、候補資料、暫定結論、推論過程に適用する。
`RequestCoordinator`のqueue、rate gate、cooldown、利用量、cache判定、runtime leaseなどの
通信制御状態は独立性の対象にせず、Agent・taskをまたいで共有できる。ただし、初回独立探索中に
一方のAgentの検索語、検索結果、候補URL、検索結果cacheを他方へ渡してはならない。

Agent内蔵Web検索の物理requestを観測できない場合は、Agent sessionの開始許可、同時実行数、
task・role・provider accountごとの利用枠を制御する。検索内容の独立性と通信制御状態の共有を
混同しない。候補URLの検証取得は共有`RequestCoordinator`へ戻す。

Web検索は役割を問わず必要時に許可する。通常は調査を作業者へ委譲するが、
オーケストレーター、一次レビューワー、Antigravityも、担当処理で情報不足を認識した場合は
自ら検索できる。検索した役割にかかわらず、検索結果だけから`evidence_id`を発行せず、
元資料の取得・検証を通過した情報だけを確定事実と最終結論の根拠にする。

オーケストレーター、一次レビューワー、Antigravityが最終結果へ`material`な影響を与え得る
新規資料を発見した場合は、検証後に影響を受ける作業者へ提示して限定的な応答機会を与える。
検索者がその資料を発見したことだけを理由に、他の分析や反証機会を省略しない。

## 4. 一次レビュー

一次レビューは、少なくとも次を確認する。

- 重要な数値・事実主張に有効な証拠参照がある。
- 事実、推論、仮説、評価が混同されていない。
- 自然言語の主語、対象、期間、比較基準、前提、条件、不確実性が明確であり、
  最終評価または人間の判断材料に影響する複数の合理的な解釈が生じない。
- 中期・長期それぞれについて、5観点、重要リスク、反証条件、欠損、モデル間不一致が
  扱われ、異なる期間の評価が単一評価へ統合されていない。
- エントリー参考条件、価格上の撤退参考条件、投資仮説上の撤退条件が区別され、
  短期的な株価方向の評価または特定価格での売買指示として表現されていない。
- 使用した `evidence_set_version`、`evidence_frozen_at`、`freshness_checked_at`、対象期間、
  鮮度、通貨、単位が整合している。
  ドル換算系列を使う場合は、USD/JPYの向き、価格種別、同一東京日付の結合、観測時刻、
  換算式、欠損時に別日の為替で補完していないことが整合している。
- 評価Policyの適用と期間別の評価可否・4段階評価の理由が整合している。
- 出力スキーマと安全境界に違反していない。
- Agent別の探索記録、候補資料の検証結果、共通証拠への採否、差し戻し後の再分析を
  追跡できる。

次をすべて満たす場合だけ一次レビュー合格とする。

1. 構造化出力と証拠参照の検証が成功している。
2. `critical` または `high` の未解決指摘がない。
3. `medium` 以下の未解決指摘は最終評価へ重大な影響を与えず、残置理由が記録されている。
4. 再調査または争点化が必要な指摘の処理が完了している。
5. レビューワーと異なる処理を採用した場合、その理由とPolicyが記録されている。

`high`または`critical`の指摘を解決済みにできるのは、次のいずれかを満たす場合に限る。

1. 指摘対象を修正し、一次レビューワーが再確認で解決を認めた。
2. 一次レビューワーが根拠付きで指摘を撤回または`medium`以下へ変更した。
3. 承認済みPolicyに従うエスカレーションまたは人間判断が、理由と証拠を記録して指摘を閉じた。

オーケストレーターが指摘を単独で`不採用`にしても、一次レビューワーが`high`または`critical`を
維持する間は解決済みとしない。`disputed`として争点化し、追加監査の起動条件を満たさない場合も
人間判断待ちへ送る。オーケストレーターまたは一次レビューワーが単独で重要度を下げて
レビュー合格条件を回避してはならない。

指摘ごとに、受け入れ、限定再調査、不採用、争点化のいずれかと理由を保存する。
すべての指摘IDは、解析完了前に重複なく1つの終端処理へ到達しなければならない。
`high`または`critical`の不採用は終端処理ではなく、争点化または人間判断への中間処理とする。

一次レビュー後は、オーケストレーターの指摘応答と一次レビューワーによる再確認を、
指摘単位の構造化された合議として反復できる。MVPでは合議往復数および再レビュー回数に
固定上限を設けない。一次レビューワーの指摘または再確認と、それに対するオーケストレーターの
応答を1往復として数え、10往復を使用量分析の参考値として記録する。10往復の超過だけを
理由に合議を停止したり、指摘を解消済みと扱ったりしない。

各往復では、使用トークン、変更した主張・評価、追加または変更した証拠参照、解消した指摘ID、
未解決の指摘IDを記録する。合意を終端条件にはせず、各指摘が受け入れ、不採用、限定再調査、
争点化のいずれかへ到達するまで処理する。オーケストレーターが通常の合議だけでは
`material`な不一致を解消できないと判断した場合は、往復数にかかわらず争点化できる。
初期運用の実測で往復数または使用量の無駄が問題になった場合に、固定上限、進捗判定、
平行線判定の追加を再検討する。

指摘の重要度は次の基準で判定する。

| 重要度 | 基準 |
| --- | --- |
| `critical` | 安全境界、秘密情報、利用規約、評価fixtureへの将来情報混入、証拠集合の不正、または成果物全体の有効性を損なう |
| `high` | いずれかの期間の4段階評価、評価可否、主要仮説、重大リスク、重要な数値・事実主張が変わり得る |
| `medium` | 結論を直ちに変えないが、説明、欠損、不確実性、証拠対応の重要な修正を要する |
| `low` | 意味を変えない表記、構成、または軽微な明確化である |

重要度は文体やモデルの確信度ではなく、修正しない場合の影響で決める。
文体・表現上の問題であっても、意味、評価、安全境界、または人間の判断が変わり得る場合は、
単なる`low`の表記修正として扱わない。

## 5. 証拠収束と限定再調査

- 初回の独立探索後、各作業者の候補資料を重複排除して承認済みデータ取得・検証工程へ渡す。
- 検証済み資料の和集合を共通証拠へ追加し、両作業者へ同じ追加証拠を差し戻す。
  発見元、棄却資料、棄却理由を失わない。
- 共通証拠を更新するたびに `evidence_set_version` を更新し、追加前の版に依存する成果物のうち
  materialな影響を受ける範囲を無効化する。
- 差し戻し後の再分析では、追加証拠の影響を受ける主張、期間別評価、リスク、反証だけを
  更新し、相手の初回分析または暫定結論を渡さない。
- 一次レビューワーがWeb検索で追加資料を発見した場合も、直接レビュー根拠に採用せず、
  候補資料として同じ取得・検証工程へ戻す。
- 再調査は、指摘または争点の解消に必要な証拠・主張へ対象を限定する。
- MVPでは1銘柄につき1回の再調査バッチを上限候補とする。
- 再調査後は、影響を受けた主張、評価、レビュー指摘だけを再評価する。
- 再調査後の再レビューは、一次合議の往復として扱い、固定回数で打ち切らない。
- 再調査バッチ数と一次合議の往復数を別々に計数し、再レビューや証拠を追加しない
  指摘応答を再調査バッチとして数えない。
- 上限後も重要事項が未解決なら、条件を満たす争点だけ追加監査へ送り、
  それ以外は人間判断待ちまたは `not_evaluable` にする。

## 6. 争点分類と重要度

| 分類 | 通常の処理 | 追加監査候補 |
| --- | --- | --- |
| 事実誤認 | 元データ照合または限定再調査 | いいえ |
| 根拠不足 | データ取得、`not_evaluable`、限定再調査 | いいえ |
| スキーマ・形式違反 | 機械検証と修正再出力 | いいえ |
| 評価基準の適用差 | Policy照合 | 解消せず影響が重大な場合 |
| 論理的な飛躍 | 推論と証拠の再構成 | 解消せず影響が重大な場合 |
| 将来仮説の相違 | 前提と反証条件の明示 | 影響が重大な場合 |
| リスク重要度の相違 | 共通基準で再評価 | 影響が重大な場合 |
| 文体・表現 | 通常修正 | いいえ |

意味または判断を変え得る曖昧さは、単なる文体・表現の問題として分類せず、影響する内容に応じて
評価基準の適用差、論理的な飛躍、将来仮説の相違、またはリスク重要度の相違として処理する。

`material` は、争点の解決方向によっていずれかの期間の4段階評価、主要投資仮説、
重大リスク、エントリー・撤退判断の重要な参考情報、または人間の最終判断材料が
変わり得る状態とする。

## 7. Antigravity追加監査の起動条件

次をすべて満たす場合だけ起動する。

1. 一次レビュー、指摘応答、許可された限定再調査が完了している。
2. 双方の主張と根拠を持つ未解決争点がある。
3. 事実確認またはスキーマ修正だけでは解消できない。
4. 最終結果への影響が`material`である。
5. 匿名化した中立な争点パケットを構成・検証できる。
6. 時間、トークン、金額、回数の上限内である。
7. 同じ争点をAntigravityで監査済みではない。

Antigravityの認証、到達性、利用枠は、上記の起動条件を満たした後、監査開始直前に確認する。
監査を必要としないtaskではAntigravityが利用不能でも通常処理を停止せず、未起動理由を記録する。
監査が必要と判定された後に利用不能が判明した場合だけ、人間判断待ちへ進む。

MVPでは、1タスクにつきAntigravityの論理監査を最大1回とし、対象銘柄に属する
最大3争点を1つの監査セッションへまとめる案を採用候補とする。各争点の論理監査は
1回限りとする。複数銘柄にまたがる比較争点の監査はMVPの対象外とし、比較機能を
実装するリリースで別途契約を定める。

起動失敗またはスキーマ修正を含む物理的なCLI実行は、初回を含めて最大2回とし、
別々の再試行枠として加算しない。正確な計数単位と上限は承認前に確定する。

Antigravityは通常作業者、常設レビューワー、単純多数決の第三票として使用しない。
Codex系またはClaude系の追加セッションを第三者監査の代替として表示しない。

## 8. 監査の実行境界

- 読み取り専用の争点専用ワークスペースを使う。
- 対象争点、適用Policy、その争点に必要で外部処理が承認済みの共通証拠だけを渡す。
- リポジトリ全体、他銘柄、作成主体名、会話履歴へアクセスさせない。
- Agent内蔵Web検索は、争点の事実確認、反証、論理監査に必要な範囲で使用できる。
  検索結果を監査判断の確定根拠にせず、検索記録と候補URLを監査結果へ含める。
- 候補資料はオーケストレーターが同じ取得・検証工程へ戻し、有効な追加証拠を
  Codex系・Claude系へ差し戻して影響範囲を再分析させる。
- ファイル更新、シェル実行、Agentによる未検証資料の証拠集合への追加を無効にする。
- 出力をスキーマ検証し、争点外の結論や無出典の新規事実を採用しない。

## 9. 監査結果の適用決定表

| 監査結果 | 証拠状態 | 原則的な処理 |
| --- | --- | --- |
| AまたはBを支持 | 既存証拠で十分 | 支持理由とPolicy適用を検証し、該当案を採用または修正する |
| どちらも支持しない | 両者に修正余地 | 両案を修正し、条件付き合格、不合格、人間判断待ちのいずれかへ進む |
| 判断不能 | 追加証拠を取得可能 | 上限内なら限定再調査。上限到達後は人間判断待ち |
| 判断不能 | 追加証拠を取得不能 | 人間判断待ち。人間が明示的に処理するか、`material` でないと再判定するまで評価を確定しない |
| 人間判断を推奨 | 価値判断・方針判断が必要 | 両論と証拠を添えて人間へエスカレーションする |
| スキーマ不正・実行失敗 | 監査結果を利用不能 | 同じ設定で1回だけ再実行し、失敗時は人間判断待ち |

監査結果は拘束的な最終判定ではない。異なる処理を採用する場合は、理由、証拠、
適用Policyを記録し、差異が重大なら人間へエスカレーションする。

## 10. 人間へのエスカレーションと最終化

通常処理と人間向けMarkdownの生成が完了し、未解決の重大事項がない場合は、
機械可読な解析結果と人間向け成果物を `解析完了` として固定できる。`解析完了` と、
人間向け成果物を `reports/finalized-reports/` へ移送する `最終化` は別の状態とする。
最終化には、権限を持つ人間の承認記録と、承認対象となった人間向け成果物を含む
解析完了成果物のハッシュ一致を必要とする。
解析完了成果物には、最終の `evidence_set_version`、`evidence_frozen_at`、
`freshness_checked_at`、鮮度確認の検索範囲と結果を含める。

次の場合は `解析完了` へ自動遷移せず、人間判断待ちとする。

- 追加監査後も`material`な争点が解消しない。
- 重要な証拠が欠損または不一致で、承認済みPolicyだけでは `not_evaluable` を含む
  処理を一意に決められない。
- Policy、利用規約、安全境界の適用に人間の判断が必要である。
- モデル系統の独立性または必要な役割数を満たせない。
- 利用上限、認証失敗、外部サービス停止により必要工程を完了できない。
- 監査結果とオーケストレーターの処理が重大に異なる。

人間には、争点、両論、共通証拠、レビュー履歴、監査結果、未決定事項、
選択可能な次状態を提示する。人間の決定者、日時、理由を記録する。
人間の承認対象となる提示文書と最終文書の言語・形式は、
[言語と対象読者の方針](06-language-and-audience-policy.md)に従う。

## 11. 評価と実行状態

銘柄評価の4段階と評価可否は
[詳細解析MVPの範囲と成功条件](01-detailed-analysis-mvp-scope.md#5-評価と実行状態の分離)
に従う。実行状態は別概念として、少なくとも次を識別する。

- 受付・データ準備・分析・統合・一次レビュー・指摘解決
- 限定再調査・追加監査・人間判断待ち
- 解析完了・最終化・中断・取消・失敗・利用上限到達

状態ID、遷移条件、再開可能点、無効遷移はP1の契約で定義する。

合議または再レビューの途中で利用可能なトークン、時間、契約上の利用枠へ到達した場合は、
未完了の指摘を解消済みにせず、中間成果物と使用量を保存して`利用上限到達`へ遷移する。
利用上限到達だけを理由に銘柄または投資評価期間を`not_evaluable`へ変更せず、未完了の
4段階評価を確定値として外部へ提示しない。
