# 不足財務資料の追加取得範囲案

## 結論

最初に発行体公式IRの資料一覧を調べ、対象期間・提出日候補・公開URLを特定する。その結果からEDINETの取得日付と書類を固定する。日付を推測してAPI一覧を連続取得しない。

本書は取得範囲の提案であり、新しいソース承認やAPI送信を実施した記録ではない。今回の追加通信は0回。既存の財務採用、評価時刻、`analysis_ready=false` は変更しない。

## 確定した不足

[比較期間の受入結果](2026-09-27-financial-comparative-period-outcome.md)に基づく。

| 優先順 | 対象 | 探す資料・理由 |
| --- | --- | --- |
| 1 | 2024年3月期（2023-04-01～2024-03-31） | この期の年次報告を優先。2023年3月期の比較値も同時に揃う可能性がある |
| 2 | 2022年3月期（2021-04-01～2022-03-31） | この期を本文または比較値に含む年次報告。優先1の結果を踏まえて取得対象を選ぶ |
| 3 | 2023年3月期（2022-04-01～2023-03-31） | 優先1で6項目が揃わない場合の補完候補。2022年3月期の比較値を含むなら優先2と兼用できる可能性がある |
| 別枠 | 最新公表分を含む四半期・半期8期間 | 現在の保存XBRLには対象contextがない。公式一覧から公表順・期間・資料種別を確認する |

年次はまず2024年3月期と2023年3月期の報告の所在を確認し、比較値を含めた2文書で不足3期を補えるか調べる。2文書で揃うことは未確認であり、取得件数の確約ではない。サマリー項目の代用や年次値の分割で不足を埋めない。

## 「直近8期間」の整理案

[証拠方針 §5](../system-requirements/02-data-source-and-evidence-policy.md#5-mvpで必要な鮮度と対象期間)は「四半期・半期財務：証拠凍結時点で公表済みの直近8期間」を要求するが、年次を除いた四半期報告単位と半期報告単位をどう統合するかは未定義。

提案は、まず公式IRの各公表資料が明記する対象期間を一覧化し、次の区別を保つこと。

- 会計期間の開始・終了日と公表日を分ける。公表順と期間順を同一視しない。
- 第1四半期、半期／第2四半期、第3四半期を識別する。半期と第2四半期累計が同じ開始・終了日の場合、同一期間として扱う。
- 累計値を単独四半期値と呼ばない。期間差分による単独四半期の算出は今回の取得対象特定には含めない。
- 同じ期間の決算短信と法定報告、訂正・差替えを別期間として加算しない。訂正元・訂正先の関係は残す。
- 年次報告を中間の8期間へ加算しない。直近8期間の具体的な日付は、公式資料で公表済みであることを確認してから確定する。

これは期間一覧の整理方針案であり、最低要件を「EDINETにある直近8文書」へ読み替えるものではない。EDINETに対象資料がなければ、IR資料の取得・parse・採用の別実装とソース承認が必要となる。

## 第1段階：承認を求める調査範囲

対象は7203／E02144の発行体公式IRの公開資料一覧と利用条件。財務値の採用は行わない。

| 項目 | 提案する上限・制約 |
| --- | --- |
| 検索 | 発行体名・7203・決算資料／有価証券報告書を用いた公式サイト限定検索、最大3クエリ |
| 参照ページ | 公式IRのトップ・決算資料一覧・年次資料一覧・年度別一覧・利用条件、合計最大8ページ。再試行もこの上限に含める |
| 抽出内容 | 資料名、対象期間、公表日、提出日が明示される場合はその日付、公開URL、訂正表記、閲覧日時 |
| 上限到達時 | 保存した索引と未確認事項を報告して停止。日付総当たりや別ドメインへの自動fallbackなし |
| 除外 | PDF・XBRL・Excel・ZIP本文の取得、EDINET認証APIへの送信、財務値抽出、ログイン、秘密情報の送信 |
| 成果物 | 候補資料のメタデータ索引、必要期間の対応表、次段階の固定取得リストとソース条件の確認結果 |

公開一覧をWebツールで確認する限定調査として承認を求める。取得したページ全文をレポートへ転載せず、必要なメタデータと出典リンクだけを残す。この許可は財務原本の外部エージェント転送や本番ソース利用の承認を含めない。

## 第2段階：日付・書類確定後に提案するEDINET取得

現在の [source approval v2](../../config/source-approvals/edinet/v2.yaml) は `one 2026-06-10 list and one uniquely matched 7203 annual XBRL document; no retry or date scanning` に限定される。既存CLIも日付・対象年次を固定しているため、設定を変えて即座に追加取得できる状態ではない。

第1段階の結果から、送信する日付、対象期間、書類種別、最大一覧回数・最大書類回数を明示した新承認と実装計画を作る。現段階では送信日や書類IDを推定して記載しない。

維持する制約は、共有Coordinator経由、同時1・60秒間隔、再試行なし、原本ローカル保存、credential非表示、外部転送禁止。保存済み一覧・原本は同一性を検証して再利用する。対象不在・複数候補・訂正選択未解決・縦覧状態不明の場合は送信対象を勝手に広げず停止する。

新たに取得する証拠の取得時刻を過去の評価時刻へ戻さない。旧runは再現用に残し、新しいtask／確認時刻との整合を明示して別成果物を作成する。過年度taxonomy・発行体拡張の違いがあり得るため、取得成功を6項目採用成功と同一視しない。

## 今回確認した実装上の境界

- `preparation/edinet_evidence.py` と `edinet_revalidation.py`: 一覧日2026-06-10・現対象の固定選別。追加取得には別途実装変更が必要。
- `sources/edinet/document_list.py`: 年次120/130、四半期140/150、半期160/170を識別するが、対応enumの存在だけで期間充足や採用を保証しない。
- `preparation/financial_candidates.py`: 訂正関係を保持する。追加資料間の自動採用方針は未完成。
- `src/AGENTS.md` §6の更新を確認。ブロッキング事項がある場合の承認待ちに変更済み。本件のブロッキング事項はコード計画の形式的承認ではなく、新しい外部参照・送信範囲の確定である。

調査範囲の整理のみのためテストは実行していない。元証拠・ソース設定・コードへの変更はない。
